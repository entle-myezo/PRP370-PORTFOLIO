## 2. User Stories and Tasks

**Evidence:**
Based on our Business Case, I helped write the following User Stories for the WASHTRACK MVP. **[Click here to view the full Business Case document](https://github.com/ente-myezo/PRP370-PORTFOLIO/blob/main/PRP372S_Business%20_Case_WASHTRACK%20(1).pdf)**

*   **User Story 1:** As a student resident, I want to see the real-time status of washing machines (working, occupied, broken) so that I don't waste my limited laundry points on a broken machine.
    *   **Tasks:** Design database schema for machine status; Build front-end UI to display status; Write API endpoint to fetch status.
*   **User Story 2:** As a student resident, I want to report a fault with an image and timestamp so that management can fix it quickly and I can request a refund.
    *   **Tasks:** Create fault reporting form; Implement image upload functionality; Create notification system for property management.

**Reflection:**
Writing these user stories helped me understand the bridge between business requirements and technical execution. I learned that a user story must always focus on the "who" and the "why" (the value to the end-user), while the tasks focus on the "how." Breaking down the WASHTRACK features into specific technical tasks was challenging at first, but it taught me how to make large features actionable. This process was vital because it ensured we were building features that directly solved the students' problem of losing laundry points.

## 3. Product Backlog

**Evidence:**
I utilized a Kanban board (Trello) to manage our Product Backlog. Because this is a phased project, I prioritized the features based on the MVP (Minimum Viable Product) requirements. **[Click here to view the live Trello Board](https://trello.com/invite/b/69f7546ec920bc93637c9b4e/ATTI0786147c7ede225e95bb606ee99cd591FB7D1E06/washtrack-logbook)**

*   **High Priority (Phase 1 MVP):** Real-time machine status, Fault reporting system.
*   **Medium Priority (Phase 2 Integration):** Booking system for machine reservations, Push notifications.
*   **Low Priority (Phase 3 Expansion):** Automated refunds via South Point API integration.

**Reflection:**
Compiling the Product Backlog taught me the critical Agile principle of prioritization. Initially, we wanted to build everything at once, but I learned that the Product Backlog must be ordered by business value. By prioritizing the real-time machine status and fault reporting as "High," we ensured that the most pressing financial pain point for students was addressed first in our MVP. I now understand that a product backlog is never truly "finished" and must constantly evolve as requirements change.

## 4. Sprint Backlog

**Evidence:**
For our first two-week sprint, we selected the highest-priority item from the Product Backlog: *Real-time machine status*.
*   **Sprint Goal:** Deploy a web page where students can see if a machine is Working, Occupied, or Broken.
*   **Sprint Tasks:** 
    1. Sketch UI wireframes (Designer)
    2. Set up MongoDB database collections (Developer)
    3. Build the Node.js API to serve status data (Developer)
    4. Write user testing documentation (Researcher)

**Reflection:**
Creating the Sprint Backlog forced our team to be realistic about what we could achieve in a short timeframe. As the Agile Lead, I learned that a sprint backlog must be actionable and owned by the team. By breaking the sprint down into daily tasks, we were able to track our velocity. I learned that if a sprint backlog is too ambitious, it leads to burnout. Therefore, we limited the sprint to only the most critical MVP tasks, which improved our delivery frequency.

**Evidence:**
The following is an excerpt from our daily stand-ups and sprint retrospective:

*   **Daily Stand-up (Day 3):**

    *   *What I will do today:* Write the User Stories based on the research data.

*   **Sprint Retrospective (End of Sprint 1):**
    *   *What went well:* The team communicated effectively via our WhatsApp group, and we successfully delivered the MVP web app.
    *   *What didn't go well:* We initially struggled to merge our code changes because we didn't review each other's work.
    *   *Action Item:* Enforce the "Definition of Done" rule—no code merges without a peer review. 

**Reflection:**
Maintaining the Agile Logbook was one of the most valuable parts of this project. It taught me that Agile ceremonies are not just meetings—they are tools for continuous improvement. I learned that the Sprint Retrospective is the safest space to admit what went wrong. When we realized our code-merging strategy was failing, the retrospective allowed us to implement a solution (peer reviews) without blaming individuals. This taught me the importance of transparency and adaptiveness in a team setting.
